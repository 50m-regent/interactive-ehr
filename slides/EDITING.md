# Marpスライド手編集ガイド

スライド本文は標準Markdownで書き、見た目は`theme/research.css`に任せます。HTMLタグとインラインCSSは使いません。

全レイアウトの表示例は`examples/component-gallery.md`にあります。

## 編集と出力

```bash
cd slides
npm ci
npm run dev
```

ブラウザでプレビューしながら`YYYY-MM-DD/slides.md`を編集します。

```bash
npm test
npm run check -- YYYY-MM-DD/slides.md
npm run build -- YYYY-MM-DD/slides.md -o YYYY-MM-DD/slides.pdf
npm run render -- YYYY-MM-DD/slides.md -o .render/slides.png
```

## 旧版からの更新

テンプレート0.5.0では、参照PDFからの再構成用レイアウトと、frontmatter、画像、キャプションの検査が追加されます。スキル側から次のように更新します。

```bash
uv run python scripts/scaffold_project.py \
  --project /path/to/project \
  --upgrade-shared
```

管理対象の旧版と一致する共有ファイルだけを更新します。手編集したテーマ、検査スクリプト、ガイドは保持します。

## 1枚の基本構造

スライドは`---`で区切ります。`_class`コメントでレイアウトを選びます。

```markdown
<!-- _class: procedure -->

# 検証の進め方

1. 条件を固定する
2. 実験を行う
3. 結果を比較する

---

# 次のスライド

通常の本文
```

先頭のYAMLはデッキ全体の設定です。

```yaml
---
marp: true
theme: research
paginate: false
title: "発表タイトル"
author: "氏名"
lang: "ja"
---
```

ページ区切りMarkdownと参照PDFから派生デッキを作る場合は、元Markdownを別ファイルへ複製し、次のクラスも追加します。元Markdownは変更しません。

```yaml
class: reference-rebuild
```

このクラスでは、元Markdownの斜体を朱色、太字を濃紺で表示します。全ページへ内容に合う`_class`を付けます。

## 基本Markdown

| 書くもの | Markdown | 用途 |
| --- | --- | --- |
| スライドタイトル | `# タイトル` | 濃紺の大見出し |
| 小見出し | `## 小見出し` | レイアウト内の区分 |
| 強調 | `**重要な結果**` | 朱色の強調 |
| 非選択 | `~~過去の項目~~` | 青灰の補足 |
| 箇条書き | `- 項目` | 補足や列挙 |
| 番号付きリスト | `1. 項目` | 手順、進捗、日程 |
| 表 | `｜項目｜内容｜` | ラベル行や比較 |
| 状態 | `` `検証中` `` | カード右側の状態ラベル |
| 画像 | `![説明](assets/image.png)` | 図、グラフ、画面画像 |
| 引用 | `> 出典または説明` | 出典や説明枠 |

## 表紙

```markdown
<!-- _class: cover -->

# 対話的グラフ構造化を用いた診療記録の可視化

###### 研究ゼミ · 2026-07-17

#### 京都大学大学院 · 氏名
```

上から60%が濃紺、残りが白になります。タイトルの下端は白背景との境界に接します。題目が長い場合は行末のバックスラッシュで改行します。

```markdown
# 対話的グラフ構造化を用いた\
診療記録のタスク駆動型可視化
```

## 章一覧

```markdown
<!-- _class: section -->

# Research Theme

- **Architecture**
- Methods
- Procedure
```

現在の章を1つだけ太字にします。太字の章だけが白、ほかの章は青灰になります。最初の章を現在位置にする場合は、見出しを`# **Research Theme**`と書き、一覧内では太字を使いません。

## ラベル付き情報行

```markdown
<!-- _class: summary -->

# 研究テーマ

| 項目 | 内容 |
| --- | --- |
| 背景 | 必要な情報が複数画面へ分散している |
| 目的 | 情報探索に必要な操作を減らす |
| 方法 | タスクに合わせてUIを生成する |
```

現在位置だけを濃紺にする場合は`focus`を併用し、対象ラベルを太字にします。

```markdown
<!-- _class: summary focus -->

# 研究テーマ

| 項目 | 内容 |
| --- | --- |
| 背景 | 情報探索に時間がかかる |
| **目的** | 必要な情報だけを提示する |
| 方法 | タスクに基づいてUIを生成する |
```

ラベルを明るい朱色にする場合は`accent-labels`を使います。

```markdown
<!-- _class: summary accent-labels -->
```

斜体にした非選択ラベルを青灰にする場合は`inactive-labels`、長いラベル用に左列を広げる場合は`wide-labels`を使います。

```markdown
<!-- _class: summary inactive-labels -->

| 項目 | 内容 |
| --- | --- |
| *背景* | すでに説明した内容 |
| 目的 | 今回説明する内容 |
```

```markdown
<!-- _class: summary accent-labels wide-labels -->
```

3列以上の表は通常の表として表示されます。

要約表は内容に応じた幅になり、見出しを除く表全体がスライドの縦横中央へ配置されます。

ラベルが不要な近況や研究質問は、`summary`に短い箇条書きまたは番号付きリストを書きます。

```markdown
<!-- _class: summary -->

# 研究質問

1. どの誤りが残るか
2. どこまで自動で直せるか
```

## 主張と結論

```markdown
<!-- _class: statement -->

# 背景

| 項目 | 内容 |
| --- | --- |
| 背景 | 固定画面では必要な情報を複数画面から探す |

| 現状 | 課題 |
| --- | --- |
| オーダー管理として実装 | **可視化の観点では不十分** |

> 必要な情報を適切に可視化して探索負荷を減らす
```

最初の表が上部ラベル行、2番目の表が中央比較、引用が下部の結論になります。
3要素は一つのまとまりとしてスライド中央へ配置されます。

## 横方向の処理フロー

```markdown
<!-- _class: pipeline -->

# UI生成の流れ

1. **タスク**

   診療時に達成したい内容

2. **データ**

   タスクに必要な記録

3. **UI**

   一覧表示または時系列表示

**入力から表示までを同じ条件で確かめる**
```

番号付きリストを3列から5列で使います。各項目の最初の太字が朱色のラベルになります。
各項目は2pxの枠線で囲まれます。項目名が意図せず折り返す場合は、文字を小さくせず、項目名を短くするか項目数を減らします。
本文ブロックはスライド中央へ配置されます。
カードの下に結論を置く場合は、短い太字の段落にします。`citation`は出典を下部へ置く場合だけ使います。

## 縦方向の手順

```markdown
<!-- _class: procedure -->

# 研究の進め方

1. UI生成システムを作成 `実装`
2. タスクからデータを集める方法を検討 `検証`
3. ユーザ入力からタスクを認識
```

項目末尾のインラインコードが右側の状態ラベルになります。

最後の項目を朱色にする場合は`flow`を使います。

```markdown
<!-- _class: flow -->
```

## 手順と説明枠

```markdown
<!-- _class: procedure callout -->

# 修論に向けた実験計画

1. 有識者へ意見聴取
2. タスクグラフを作成
3. 生成UIを評価

> ## 効果検証実験
>
> 1. 医療従事者へ協力を依頼する
> 2. 提案システムを複数シナリオへ適用する
> 3. 従来画面との操作差を比較する

タスクベースのUI生成から検証を進める
```

手順が左、引用の説明枠が右、最後の段落が右下の結論になります。

## 並行する二つの手順

```markdown
<!-- _class: parallel -->

# 今後の進め方

## UI生成の検証

1. シナリオ作成を依頼
2. グラフを作成
3. UI生成を評価

## 自動生成モデル

1. モデルを設計
2. シナリオを追加
3. グラフ生成を評価

二つの実験を並行して進める
```

小見出しと番号付きリストを2組書きます。

## 目次と題目案

```markdown
<!-- _class: agenda -->

# 中間発表会題目案

1. タスクベースの電子カルテUI自動生成手法
2. タスクのグラフ構造化に基づくUI生成

   - グラフ構造化を中核技術とする
   - 入力に応じてUIを更新する

3. 電子カルテのユーザ体験向上手法
```

番号付き項目の中に箇条書きの補足を置けます。

## 左右比較

```markdown
<!-- _class: comparison -->

# 実験条件

1. **従来UI**

   固定された画面を横断して情報を探す。

2. **提案UI**

   タスクに必要な情報をまとめて表示する。
```

右側の枠が朱色になります。

## 3要素の構成

```markdown
<!-- _class: architecture -->

# システム構成

1. **タスク認識**

   ユーザ入力から診療タスクを得る。

2. **データ収集**

   タスクに必要な記録を取得する。

3. **UI生成**

   タスクとデータに合う表示を生成する。
```

上段に2項目、下段に1項目を配置します。複雑な構成図は画像にします。

## 進捗

```markdown
<!-- _class: progress -->

# 現在の実装

1. シナリオからタスクを抽出 `完了`
2. タスクグラフを作成 `確認中`
3. グラフからUIを生成
```

状態ラベルがない項目も書けます。

## 日程

```markdown
<!-- _class: timeline -->

# スケジュール

1. 予備実験 `2026年12月`
2. 学会抄録の提出 `2027年1月`
3. 修士論文の執筆
4. 学会発表 `2027年5月`
```

5項目程度までを縦に並べます。

```markdown
<!-- _class: labeled-sections -->

> 対象となる診療状況を示す

> 患者の状態を確認して対応を決める
```

## 説明枠

```markdown
<!-- _class: callout -->

# 次の判断

> ## 確認すること
>
> - 操作回数が減るか
> - 情報の見落としが増えないか
> - タスクごとの差を説明できるか
```

## 書き方

- 1枚につき伝えたいことを1つに絞ります。
- タイトルは原則1行にします。
- 強調色は結論、差分、現在位置に使います。
- 目次と題目案には`agenda`を使います。
- 横方向の処理には`pipeline`、時系列の手順には`procedure`を使います。
- 背景、目的、方法には`summary`を使います。
- 複雑な図は画像として用意し、`visual`で配置します。
- 画像の直後には通常段落でキャプションを書きます。
- 二つの画像を比べる場合は`visual-pair`を使います。
- raw HTML、インラインCSS、外部スクリプトは書きません。
- PDF出力前にMarkdown検査、PNG出力、原寸確認を行います。
