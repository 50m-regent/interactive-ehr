# 正しい組み合わせを1か所だけ壊した

1. 質問と正解SQLから基準を作る
2. SQLを実行して結果と表示方法を決める
3. 対応を1か所だけ意図的に壊す
4. 4種類の確認方法へ同じ候補を渡す

正しい候補と不整合候補を対にして、見逃しと過剰な拒否を分けて測った

---

<!-- _class: summary wide-labels -->

# 8種類の不整合を作った

| 変更する場所 | 内容 |
| --- | --- |
| 質問とSQL | 患者、対象項目、期間、集約方法 |
| SQLと情報源 | 参照したデータの説明 |
| 結果と表示 | 表示方式、データと画面の接続 |
| SQLと実行結果 | 更新後も古い結果を残す |

すべて、SQLを実行でき、画面にも表示できる候補として作成

---

<!-- _class: progress -->

# 4種類の確認方法を比べた

1. 局所確認：SQLや画面部品が単独で動くか
2. 成果物ごとの契約：SQL、結果、画面部品が個別に整合するか
3. グラフ契約：質問から表示までの対応がつながるか
4. サイドカー契約：同じ対応を1枚の表として照合できるか

グラフとサイドカーには同じ確認内容を持たせた

# 個別の整合性と全体の整合性は別だった

1. 成果物ごとの契約

   情報源、表示方式、古い結果は検出できた

   患者、対象項目、期間、集約方法、誤接続は十分に扱えなかった

2. 層をまたぐ契約

   8種類すべてを検出した

   問題箇所の特定と1回の修復も763件すべてで成功した

<!-- _class: comparison -->

# 主張できることと、まだ主張できないこと

1. 主張できること

   個別確認だけでは、層をまたぐ不整合を見逃す

   明示した対応関係は、不整合の検出、場所の特定、1回の修復に使える

2. まだ主張できないこと

   グラフ形式が平坦な表より優れている

   実際の生成モデルや医療現場でも同じ性能になる

   臨床上の安全性や使いやすさが向上する

---

# CHIでは契約内容の効果として説明する

| 中心 | 内容 |
| --- | --- |
| 問題 | 正常に動く部品の間で意味の対応が壊れる |

| 示せたこと | 示していないこと |
| --- | --- |
| 層をまたぐ契約で不整合を検出 | グラフ形式だけによる性能向上 |
| 正しい候補は拒否しなかった | 複数不整合や生成モデルへの一般化 |
| 問題箇所を特定して1回の修復 | 臨床的な有効性と安全性 |

> TraceBench-EHRは、質問から表示までの対応を再現可能に評価する技術基盤
