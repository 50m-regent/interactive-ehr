## 書きたい主張と、必要な証拠を対応させる

目指す主張は、利用者が変える条件と維持する条件を引き継ぎ、取得から表示まで確認することで、意図しない変更を減らせることです。さらに、条件の変更点と検査の根拠を示すことで、利用者の確認と修正を支援できるかを調べます。どちらも未検証の仮説です。

| 実験 | 答える問い | 主に比較するもの | 主指標 |
|---|---|---|---|
| 同じ候補に対する検査 | 簡単な検査が見逃す不適合を追加で検出できるか | SQL条件の検査と、複数状態での結果・表示の検査 | 不適合候補の受理割合と、適合候補の拒否割合 |
| 実アプリの連続更新 | 検査を組み込むと、要求した更新を正しく完了できるか | 累積条件を渡す生成、簡単な検査付き、結果・表示の検査付き | 全4更新を適合状態で完了した系列の割合 |
| 利用者による確認・修正 | 検査の根拠を整理して示すと、誤りを残した確定を減らせるか | 同じ検査結果を一覧で示す画面と、変更点・対応箇所を示す画面 | 不適合な画面を修正せず確定した割合 |

9月8日までの[単発20件](../chi-generated-update-20260908/REPORT.md)と[連続12試行](../chi-sequential-update-20260908/REPORT.md)では、簡単な検査との差は出ませんでした。32試行には同じ系列の状態が含まれ、32個の独立標本ではありません。これらは実装と採点の開発資料に使い、最終評価の件数には含めません。

## 実験前に直すことと、条件の決め方

生成先のJSONスキーマとアプリ内の必須条件を合わせ、表示種別の変更が更新計画へ反映されるようにします。保存した失敗応答を再生し、不正な空のMarkdown部品を受理しないこと、折れ線への要求と計画が一致することを検証します。過去の失敗応答が修正後に拒否されても、生成の成功率が上がったとは解釈しません。

合成データ上で期間、平均、件数、単位、折れ線、患者の変更を実行し、データと表示の対応を確認します。APIエラー時と検証失敗時の扱いを決め、すべての比較条件へ同じ修正を適用します。修正前の結果を上書きしません。

各要求には、変更してよい条件、維持する条件、解除する条件を付けます。例えば「直近7日の体重を最新3件へ変更」では7日の範囲を維持します。「全期間の最新3件へ変更」では期間を解除します。単位の変更は値とラベルを同時に変え、別の表示部品の患者や期間は維持します。

合成の要求を研究者が書き、実装担当とは別の確認者が、モデル出力を見る前に条件と期待する結果を確認します。解釈が複数ある要求は、確認を求めることを正解とする別の開発用集合へ置き、今回の主評価では明示的な要求に限ります。臨床タスクの妥当性や重大性を付ける場合は、医療の専門家による確認が必要です。Codex内の別処理だけを、独立した人の確認と呼びません。

条件を常に正しく渡せるとは仮定しません。検査単体の実験では確認済み条件を共通入力とし、連続更新の実験では履歴から自動抽出した条件を共通入力とします。後者では抽出の誤りも測り、手作業で正解へ置き換えません。

## 同じ候補に対して、検査の追加価値を測る

### 課題を6種類から作る

新しい開発用12系列と、評価用48系列を準備し、各系列を4回の更新で構成します。評価用は各種類8系列とし、4系列は条件の維持を中心に、残る4系列には条件を明示的に解除・変更する要求を入れます。データの数値だけを変えた同一テンプレートを、独立した系列として水増ししません。

| 課題の種類 | 4回の更新の例 | 主に確認する対応 |
|---|---|---|
| 期間と最新件数 | 7日へ変更 → 最新3件 → 全期間へ変更 → 14日へ変更 | 期間の維持と意図した解除 |
| 患者と複数表示 | 左の患者を変更 → 左の期間を変更 → 右を折れ線へ変更 → 左を元の患者へ戻す | 対象と対象外の部品の分離 |
| 集約と欠損 | 平均へ変更 → 別期間へ変更 → 有効値の件数へ変更 → 個々の値へ戻す | 集約、NULL、空結果 |
| 単位と表示値 | kgからg → 最新件数へ変更 → 折れ線へ変更 → kgへ戻す | 値、単位、軸の一致 |
| 表示形式と接続 | 表から折れ線 → 表示項目を変更 → 別の部品を追加 → 最初の部品の期間を変更 | 軸、参照先、対象外の部品 |
| 取得時点と順序 | 新しいデータへ更新 → 昇順へ変更 → 最新件数へ変更 → 上限を解除する | キャッシュ、取得版、行の選択と順序 |

ここにある要求は例です。実行用の文章、対象ID、初期状態、時点の定義、タイブレークは課題作成時に固定します。並べ替えだけでは値の集合を変えない、最新件数を変えるときは日時の同値をIDで解決するなど、採点可能な規則を記します。

### 生成条件をそろえて、同じ候補を4種類の検査へ渡す

評価用48系列 × 4更新 × 2モデル × 2反復で、768回の生成を予定します。失敗して候補を得られない試行も件数へ含めます。モデルは生成時点で利用可能な版を固定します。これは単一モデルの結論が別モデルでも成り立つかを見る比較であり、モデル全般の性能を推定する標本ではありません。

各更新では、直前まで正しく更新された参照状態から候補を一度だけ生成します。自然言語の履歴、今回の要求、初期条件を渡し、採点ラベル、参照SQL、採点用DBは渡しません。この実験は、前の誤りが残る影響を除いて検査器を比べます。連続利用の性能は次の実験で調べます。

| 検査 | 共通部分に追加する内容 |
|---|---|
| 構造と実行 | 追加なし |
| 簡単なSQL条件 | 患者、期間、項目、集約、単位、順序、件数の構文木による検査 |
| 1状態の結果と表示 | 簡単なSQL条件を置き換え、現在のDBで条件から計算した期待値と実行結果を比較する |
| 3状態の結果と表示 | 現在のDBと2個の対照DBで結果を比較する |

共通部分は、スキーマ、SQL実行、参照先・列・軸の存在、SQLの再実行結果とキャッシュの一致、指定された表示種別・単位・対象外の部品の保持です。表示の問題だけを提案側で検査して差を作らないようにします。簡単なSQL条件の検査にも同じ累積条件を渡します。既存の構文木検査を基礎とし、対応するSQL構文と未対応時の判定を開発用課題で固定します。

結果の検査は、書き方が異なっても必要な結果が一致すれば受理します。複数状態で一致しても、任意のSQLの同値性を証明したとは扱いません。グラフと表形式で同じチェックを実装した比較は、今回の主比較に追加しません。

採点には検査が使わない3個のDB状態と、別実装の参照計算を使います。境界値、対象外の患者、同じ日時、NULL、空結果、追加された行を含めます。独立した確認者がDBと期待値の対応を確認します。検査用DBと採点用DBを別ファイルにするだけでは独立性を保証できないため、共有する仕様と実装を一覧にします。

新規生成と別に、正しい別解12件と既知の誤り12件、計24件の診断用候補を用意します。各種類に正しい2件と誤り2件を置き、値の変更や意図した条件解除を確認します。人工候補の結果は生成された候補の検出性能へ合算しません。既存の32試行も同様に別集計です。

### 分母を分けて比較する

主比較は、3状態の検査と簡単なSQL条件の検査です。構造・実行との比較、1状態と3状態の比較は副次比較です。

- 不適合候補の受理割合は、処理が完了した不適合候補のうち検査が受理した数を分子にします。
- 適合候補の拒否割合は、処理が完了した適合候補のうち検査が拒否した数を分子にします。
- 生成処理の失敗、形式検証の失敗、SQL実行の失敗、未実行は、それぞれ別の分母と件数で示します。
- 同じ候補に対する判定差、判定が分かれた原因、検査時間、必要な参照情報を保存します。

不適合が得られなかった層では見逃し割合を0とせず、推定不能とします。主な対比は、見逃しの減少と過剰拒否の増加を一緒に示します。計画上の過剰拒否の許容差は2パーセントポイントを仮置きします。これは臨床上の安全基準ではなく、追加の検査に見合うかを考える研究上の目安であり、本評価前に根拠とともに確定します。

## 実アプリで更新を続け、完了と誤りの残存を測る

検査単体とは別の評価用24系列を準備します。6種類につき4系列、各4更新です。各種類の半分には条件を解除する要求を含めます。検査単体の結果を見てから、提案手法が有利な系列を選びません。

24系列 × 4更新 × 2モデル × 2反復 × 3条件で、1,152更新試行を予定します。同じモデル、乱数設定、初期状態、履歴、累積条件、SQL環境を使い、生成器の修正も共通にします。

| 条件 | 生成への入力 | 候補を画面へ反映する条件 |
|---|---|---|
| 累積条件を渡す生成 | 履歴、現在の画面状態、自動抽出した累積条件 | 共通の構造・実行検査を通る |
| 簡単な検査を加える | 同上 | 共通検査とSQL条件の検査を通る |
| 結果と表示の検査を加える | 同上 | 共通検査と3状態の結果・表示の検査を通る |

累積条件は自然言語の要求履歴から、生成器とは別の固定した処理で更新します。モデル・反復ごとに同じ要求列から384回分の条件抽出を行い、その出力を3条件で共有します。抽出処理は生成画面や採点結果を見ません。各時点の条件を確認済みの条件と比較し、全条件一致、項目ごとの欠落・誤変更、抽出失敗を報告します。これにより、正しい条件を得る負担と失敗を結果から隠しません。

反映しない場合は、最後に反映した状態を保ち、更新が未完了であることを記録します。今回の実験では自動修復や再生成を入れません。次の要求は予定どおり累積し、古い画面の状態と新しい累積条件から次の生成を行います。条件抽出に失敗した回は全条件で更新未完了とし、次の回には全履歴から再抽出します。この進め方は固定した要求列の技術評価であり、失敗後に人がどう操作するかを表すものではありません。

主指標は、4回すべてでその時点の要求を満たして完了した系列の割合です。全件を拒否する方式は0になります。最終状態だけが適合した系列、最初に不適合が反映された位置、不適合が残った手数、正しい候補の拒否、更新未完了、API呼出・トークン・待ち時間も示します。要求未達の古い画面を保つことと、誤った新しい画面を反映することは分けます。

主比較は簡単な検査付きと結果・表示の検査付きです。ここで差がなく、検査単体でも追加価値がなければ、検査方法の優位性を中心にした主張は支持されません。利用者向けの説明を改善する研究へ進む場合も、別の仮説として扱います。

## 利用者が誤りを見つけ、修正できるかを測る

技術評価と、倫理手続き・課題確認を終えた後の計画です。現在の `data/evaluation/ito_case_manifest.v0.1.json` は臨床内容が未記入のテンプレートで、人対象の開始条件を満たしていません。

臨床上の利用を主張するなら、対象は電子カルテを利用する医療者とします。人数は予備4名、本評価24名を募集可能性を考える初期案とし、予備の参加者は本評価へ含めません。一般の参加者へ替える場合は、研究対象を非臨床のデータ確認へ変更し、医療者への効果を主張しません。必要人数は、意味のある見逃し減少量、参加者と課題のばらつき、予備での所要時間を使うシミュレーションで本評価前に確定します。24名で十分とはまだ判断していません。

両条件で同じ生成結果と同じ検査結果を使います。一方は、現在の取得条件と検査結果を文字の一覧で示します。もう一方は、同じ情報を変更前後の差分として整理し、要求・取得結果・表示の対応箇所へ移動できるようにします。検査器やモデルを条件ごとに変えず、説明の提示方法の効果を評価します。両条件で同じ条件編集フォームを使って修正できるようにし、課題中のモデル再生成は使いません。

一人は各条件6課題、計12課題を行います。各条件には正常3課題、不適合3課題を置きます。内容の異なる対応課題を12組、計24件準備し、一人は各組の片方だけを見ます。画面条件、課題の割当、提示順を釣り合わせ、同じ内容を見た学習効果を避けます。誤りを含む割合を調整した比較であり、実運用での誤りの頻度は推定しません。実生成から選んだ課題と人工的に誤りを入れた課題は由来を明記し、課題集合を参加者募集前に固定します。

各条件で、正常3課題のうち1課題に誤警告を、不適合3課題のうち1課題に検出漏れを入れます。残る4課題の検査結果は正しくします。両画面へ同じ警告と事実を示し、参加者には検査にも誤りがあり得ると説明します。これらは確認行動を調べるために制御した刺激であり、モデルや検査器の実際の精度には算入しません。正しい警告へ従うだけで全課題を解ける構成を避けます。

参加者は、要求を読んで画面を確認し、そのまま確定するか、条件を直して確定します。1課題180秒を上限とし、練習、12課題、短い振り返りで約60分を見込みます。予備で妥当性を確認してから制限時間を固定します。

主指標は、不適合課題で誤りを残したまま確定した割合です。正常な課題への不要な修正・拒否、正しく完了した割合、課題時間、確認箇所も測ります。時間は成功した課題だけに絞らず、時間切れを含めて報告します。時間切れは誤りの確定とは別に未完了とし、全件保留による見逃しゼロを改善と扱いません。

必要な同意、保管先、アクセス権、保管期間、撤回手順、実施許可が確認されるまで募集・実施しません。研究参加者のログや発言は公開リポジトリへ置きません。医学的判断や実患者への操作は課題に含めません。

## 分析方法と、主張を変える判断基準

技術評価は更新を独立標本として扱わず、系列を単位に、モデルと反復をまとめて再標本化します。モデル別の件数と効果も併記します。系列を再標本化した対応差の95%区間を10,000回のブートストラップで求め、検査単体の見逃しと過剰拒否、連続更新の全手順完了を別に報告します。信頼区間は今回作成した課題群内の不確実性を表し、臨床現場への代表性を与えません。

主比較は各実験で一つに固定します。検査単体では見逃し差の95%区間が改善側にあり、過剰拒否の増加について区間上限が事前の許容差以内かを確認します。連続更新では全手順完了の差と、不適合の反映・未完了の内訳を合わせて判断します。副次比較で検定を行う場合は、実験ごとの比較群を事前に列挙してHolm補正します。差が有意でないことを同等性の証拠とは扱いません。

人対象評価は参加者内の比較とし、条件、提示順、参加者、対応課題の違いを考慮します。本評価前に参加者・課題を含む混合効果モデルと周辺化した割合差の計算を固定します。モデルが安定して推定できない場合に備え、参加者単位の対応差を示す補助分析も固定し、課題全般への一般化を制限します。

| 結果 | 論文で進める主張 |
|---|---|
| 自動抽出した条件が誤り、共通して見逃す | 条件の作成・確認方法を改善する必要がある |
| 人が確認した条件でのみ検査が改善する | 信頼できる条件がある場合の技術評価に限る |
| 検査は改善するが更新完了が下がる | 検出と作業継続のトレードオフを報告する |
| 検査単体と連続更新が改善する | 評価した範囲での技術的な追加価値を主張する |
| 説明画面で見逃しと作業完了が改善する | 確認・修正の支援効果を主張する |
| 差が出ない、または区間が広い | 追加価値は未確認とし、勝つ例を探して評価集合を変更しない |

| 開発確認 | 既存32試行と人工24候補、開発用課題で処理を確かめる | 比較条件、対応構文、分母、分析が固定済み |
| 検査の本評価 | 768回の生成を試行し、得られた同じ候補を採点する | 固定した上限内で実行記録を保存する |
| 連続更新の本評価 | 1,152更新試行と384回分の条件抽出を行う | 共通入力、反映・保留の扱いが確認済み |
| 利用者の予備と本評価 | 専門家が確認した課題で二つの説明画面を比較する | 倫理手続き、募集人数、同意と保管先が確定済み |

課題の件数は、予備で得た発生率と系列内のばらつき、検出したい差、計算資源から本評価前に見直します。本評価の結果を見ながら件数を増やしません。技術評価の本評価分は合計1,920更新試行です。一つの更新に複数のAPI呼出が必要なため、呼出回数は別に見積もります。条件抽出384回と開発分も加わります。

使用モデルのAPI上の識別子、接続処理、温度、seed、入出力と推論の上限、1更新当たりの最大呼出回数、料金、総額上限はまだ未確定です。先行実験の費用をそのまま当てはめません。実装後に開発課題で必要量を測り、所要時間と保守的な費用上限を提示してから、本評価の実行計画を固定します。人対象の謝金や募集費用も別に確定します。

APIエラー、クラッシュ、入力や出力の漏えい、上限超過のおそれがあれば実行全体を停止し、自動で再実行しません。生成や意味検査の失敗は結果として保存します。解析対象から除外する理由は事前に決め、想定外の不具合では旧版と出力を保持し、新しい実行版を別に作ります。

入力、条件、モデル要求、加工前の応答、更新前後の画面状態、SQL結果とキャッシュ、描画への入力、採点、費用情報を保存します。現行の `run_sequential_update_pilot.py` は前回の固定実験用です。この計画を実行するコマンドは未作成であり、同じコマンドで実施できるとは扱いません。
