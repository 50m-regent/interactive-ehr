# 生成された更新で要求と表示の対応を調べる予備評価

ユーザーが2026年9月8日に検証まで進めるよう依頼した範囲で実施します。[Issue #53](https://github.com/50m-regent/interactive-ehr/issues/53)、[PR #51](https://github.com/50m-regent/interactive-ehr/pull/51)、[NotionのCHIタスク](https://www.notion.so/3bbc165ad0ab8124aa53ebf702a83513)で追跡します。

## 実生成で問題が起きるかを先に確認する

要求した変更を反映し、変更対象外の情報を保持できるかを調べます。実生成で誤りが起きない結果もそのまま報告します。既存の正式評価とSQL変換実験のコード・結果は変更しません。

仮説は、構造と実行の検査を通る更新にも要求と異なる取得・表示があり、明示的な要求条件を使う検査で区別できる、というものです。もう一つは、参照SQLと異なる実装でも、有限のデータ状態で要求を満たす更新がある、というものです。20件は方向を決めるための目的抽出であり、誤り率の母集団推定や検出力を保証する標本ではありません。

## 入力と正解の範囲を限定する

合成の測定テーブルだけを使います。3人分の識別子SYN_A〜SYN_C、体重kg、脈拍bpm、固定日時、欠損値、期間の境界、将来の日時を含みます。実患者やEHRSQLの行、既存原稿、認証情報はモデルへ渡しません。送るのは新しく作る非機微のスキーマ、合成の初期SQL・表示部品、更新要求だけです。

初期画面は、SYN_Aの直近1日間の体重と、保持対象の脈拍です。20件は期間4件、患者2件、並び順1件、最新件数2件、単位1件、項目1件、グラフ化1件、期間と順序2件、患者と期間2件、単位と期間2件、患者と項目1件、期間と最新件数1件です。全件が同じ初期状態からの独立した1回の更新です。要求は曖昧さを避け、日時範囲は両端を含みます。

返却物はSQLと表示仕様の小さなJSONです。既存アプリの複数回呼出しによる更新範囲判定やScenarioGraphの増分生成は通しません。表示には既存のStreamlitレンダラを使います。これは制約された生成課題であり、本アプリ全体や自然発生した臨床要求の性能とは扱いません。

## 生成前に条件を固定する

Gemini 2.5 Proを既存のVertex AI設定で20回、各要求1回だけ呼び出します。temperature 0.2、top_p 1、最大出力4096トークン、thinking_budget 1024、seedは20260908から要求順に1ずつ増やします。入力は要求とスキーマのUTF-8合計20,000バイト以下です。各呼出しのタイムアウトは120秒、SDKのattemptsは1です。API障害時は以降を止め、自動再試行しません。JSON不正や不適切な生成内容は修正・再生成せず記録し、次の要求へ進みます。

想定時間は生成5〜20分、ローカル検査数分です。ローカルCPUと既存のVertex AIを使います。料金表のGemini 2.5 Pro、入力100万トークン1.25米ドル、出力10米ドルを基に、20回の上限設定で概算2米ドル未満を見込みます。実請求は確認していません。利用トークンを応答から保存します。[Googleの料金表](https://cloud.google.com/gemini-enterprise-agent-platform/generative-ai/pricing)を2026年9月8日に確認しました。

モデルの要求名、返却された版、設定、応答、終了理由、利用トークン、時刻を保存します。seedの固定だけでクラウド生成の完全再現を保証しません。入力・実装・環境・出力のチェックサムを記録します。

## 四つの検査を同じ出力へ適用する

| 検査 | 利用する情報 |
|---|---|
| structure | 1状態でのSQL実行、IDの一意性、表示先と列・軸の存在 |
| reference | 上記に加え、要求から組み立てた参照SQLとの前後の空白・末尾セミコロンを除いた一致、表示条件の照合 |
| one_state | 要求と保持条件をPythonで解釈した期待値と、SQL実行結果・表示条件を状態0で比較 |
| three_states | 同じ比較を状態0〜2で行う |

referenceは正解SQLを利用できる特別な比較条件であり、一般的な実運用で利用できる前提にはしません。生成側とone_state、three_statesには正解SQLを渡しません。グラフと表形式の保存形式の効果は比較しません。既存の正式評価の4条件とは実装・範囲が異なります。

期待する変更・保持条件は人手で作った明示的な技術仕様であり、自然言語から自動抽出したものではありません。Pythonによる期待値計算は参照SQLを読みません。採点には状態3〜6を使い、別実装で条件から作るSQLの結果と比較します。表示条件の判定コードと要求条件は共有します。独立した専門家による正解ラベルではなく、有限の合成状態と表示規則に対する適合です。同じ結果になるSQLを一般的に同等とは扱いません。

主な記録は、採点上の適合・不適合の件数、各検査の受理件数、不適合の受理、適合の拒否です。JSON不正も評価分母へ含め、APIエラーと未実行は別記します。自然生成の結果と、動作を検証する人工的な対照の結果を混ぜません。探索的な20件のためp値や独立同分布を仮定した信頼区間は主結果に使いません。

## 実装と採点を確かめる

生成前に、患者・項目・時刻境界・順序・値・単位・保持対象・表示先の変更、結果を保つSQLの別解、1状態だけで正しいSQLを使うテストを行います。書き込み、外部参照、複文、計算量超過をSQL実行境界で拒否します。すべての参照結果について、PythonとSQLの期待値が一致することを確認します。有限の状態をすべて通っても、別の状態では誤る反例もテストに残します。

実生成後は各応答を同じ固定コードで採点し、JSON Linesから件数を別集計します。読み取れる応答は既存レンダラへ渡し、例外・警告と出力された表・グラフを確認します。これはStreamlitの描画データの確認であり、視認性や人の理解の評価ではありません。

```bash
uv run python scripts/run_generated_update_pilot.py prepare --inputs experiments/chi-generated-update-20260908/inputs
uv run python scripts/run_generated_update_pilot.py generate --inputs experiments/chi-generated-update-20260908/inputs --output results/evaluation/chi_generated_update_20260908
uv run python scripts/run_generated_update_pilot.py score --inputs experiments/chi-generated-update-20260908/inputs --output results/evaluation/chi_generated_update_20260908
```
