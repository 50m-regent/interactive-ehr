# 既存データでSQLの別解と意味変更を評価する

2026年9月7日、追加実験の実行前に条件を固定する。これは正式結果を見た後に設計した探索的評価である。[Issue #52](https://github.com/50m-regent/interactive-ehr/issues/52)と[NotionのCHIタスク](https://www.notion.so/3bbc165ad0ab8124aa53ebf702a83513)で追跡する。元の評価コードと結果は変更しない。

## 比較する候補

固定済みEHRSQL-2024 testの回答可能な934件を対象とする。各ケースについて元のSQL、前後の空白を変えた対照、元SQLを `SELECT * FROM (...) WHERE 1 = 1` で包む別解、WHERE内の列とリテラルの等号一つを不等号に変えた候補を作る。等号は構文木を深さ優先で走査し、最初に見つかる適用可能な一箇所を選ぶ。結合条件同士の比較や列同士の比較は変えない。元の文字列の演算子だけを置換し、全リテラルを保持したことを検査する。適用箇所がなければ適用不可として数える。

別解では質問、期待値、表示部品を元ケースに合わせる。変換後のSQLに、そのSQLを実行した結果と参照テーブルを結び付ける。変更前を表すノードには基準成果物を置き、変更後ノードと表示の接続を検査する。既存の8種類のペア生成や局所検査への通過を、採用条件にはしない。

## 正解の判定と除外

元SQLと変換後SQLを読み取り専用SQLiteで実行し、列名と型付き結果の多重集合を比較する。既存の正解判定関数や結果ダイジェストは、この比較に使用しない。ただし、同じデータベースとSQLエンジンを使うため、完全に独立した実験環境ではない。表示順と未知のデータベース状態での同値性は評価しない。

元SQLの構文・読み取り専用検査に失敗したケース、乱数・現在時刻などを使うケース、ORDER BYのないLIMITを持つケースは除外する。SQL一回の上限は5秒、取得上限は10,000行。実行失敗、上限到達、繰り返した基準実行との結果不一致も理由別に残す。列名が変わる変換は、結果値の比較だけで妥当と扱わず別集計にする。

包む別解は列と型付き結果が一致した場合に妥当とする。等号の反転は、列が一致して型付き結果が変わった場合だけ、基準の問い合わせから結果を変えた候補として主集計へ入れる。同じ結果だった候補は正解・不正解を推測せず別集計にする。この判定は基準SQLを要求の代理とするもので、医学的な誤りや現実の生成エラーを認定しない。

## 検査条件と指標

固定された局所・成果物内・グラフ・表形式の4条件を実行する。さらにグラフの診断からSQL一致だけ、注釈照合だけ、両方を外した受理・拒否を再構成する。この3条件は検査器を変更した再実行ではない。各条件の採用数、妥当候補の誤拒否、結果が変わった候補の流出、問題コードを数える。分母、除外、空結果、正規化後のSQL一致、テンプレート数を残す。有限のケース集合の記述とし、独立標本を仮定したp値や信頼区間を付けない。

## 実行と保存

`uv run python scripts/run_chi_sql_stress.py --dataset /private/tmp/chi-ehrsql-fixed --output results/evaluation/chi_sql_stress_20260907` を実行する。ローカルCPUで10分程度を見込む。各SQLに上限を設け、全体が30分を超えた場合は次ケースへ進まず停止する。入力のチェックサム不一致、基準候補の拒否、比較処理の不整合、出力先の既存ファイルを検出した場合も停止し、原因を確認してから再実行案を示す。
