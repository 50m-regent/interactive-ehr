# 既存データを使う追加評価

2026年9月7日。全体査読を受けて設計した探索的な追加評価である。正式結果を見た後の設計であり、事前登録した確認的評価として扱わない。固定済みの評価コードと結果は変更しない。

## 診断ログから検査の役割を調べる

主な問いは、成果物内検査に正解SQLとの一致と目標の接続先との一致を加えるだけで、既存の層間検査と同じ受理・拒否を得られるかである。もし一致すれば、この候補集合では他の検査が拒否件数を増やしたとは言えない。ただし、診断の内容や使いやすさまで同じとは言えない。

testの6,104行とvalidationの6,064行を使う。各候補について4条件が一つずつあり、ラベルと正解判定が一致し、受理が問題コードの空集合と一致することを確認する。入力ファイルと評価実装のチェックサムも、既存マニフェストと照合する。欠落、重複、不一致があれば中止する。

次の条件を、記録済みの問題コードから再構成する。

| 条件 | 拒否に使う問題コード |
|---|---|
| 層間検査の全項目 | グラフ条件の全コード |
| SQLの完全一致だけ | `target_query_mismatch` |
| 成果物内検査とSQLの一致 | 成果物内条件のコードと `target_query_mismatch` |
| 成果物内検査とSQL・接続先の一致 | 上の条件と `target_widget_connection_mismatch` |
| 成果物内検査と接続先の一致 | 成果物内条件のコードと `target_widget_connection_mismatch` |
| SQLの完全一致を除く | グラフ条件から `target_query_mismatch` を除いたコード |
| 注釈との照合を除く | グラフ条件から `semantic_` で始まるコードを除いたもの |
| SQLの完全一致と注釈の照合を除く | 上の二種類を除いたコード |
| 成果物内検査と注釈の照合 | 成果物内条件のコードと `semantic_` で始まるコード |

主要指標は不整合の流出件数と、妥当候補の受理件数。全項目の判定と異なる候補数も数える。副次的に8種類ごとの内訳を示す。testとvalidationは分けて報告し、結果をまとめて独立した母集団とは扱わない。有限の固定ログの再集計なので、p値や新たな信頼区間は付けない。

この分析は、実行した検査器から項目を外して再実行する実験ではない。現行コードが各検査を計算して最後に問題コードの有無で受理を決めることを前提に、記録から受理・拒否だけを再構成する。診断の種類、復元成功率、実行時間、計算の短絡による違いは推定しない。

ローカルCPUで実行し、外部通信は行わない。想定時間は1分以内。出力はこのディレクトリの `results-checked/` とし、集計、入力・実装のチェックサム、実行条件だけを保存する。既存の出力があれば上書きせずに停止する。

初回の試行後、入力の型検査を補い、実行コードのテストと型検査を通した版で再集計する。条件と集計式は変えない。初回の集計と完全一致することを確認し、確認済みの版を残す。

## 結果を保つ別のSQLへの対応を調べる

次に優先する実験は、正式評価と同じEHRSQL-2024の版を使い、結果を変えないSQLを層間検査が誤って拒否するかの確認である。現在の作業場所には元の注釈JSONとデモ用SQLiteが見当たらないため、固定した公開版から再取得する必要がある。

比較候補は元のSQL、前後の空白だけを変えた対照、元の問い合わせ全体をサブクエリとして包み `WHERE 1 = 1` を加えた変換とする。生成モデルは呼ばない。質問や期待値、表示部品は元のケースに合わせ、変換後のSQLの実行結果をそのSQLへ正しく関連付ける。

変換の正解判定は、注入ラベルや既存のオラクルに依存させない。問い合わせの変換規則を確認し、同じ読み取り専用SQLiteで元のSQLと変換後の列・型付き結果の多重集合が一致するか照合する。これは同じデータベース状態での結果一致であり、あらゆるデータや表示順に対する同値性の証明ではない。

全934件の回答可能ケースを対象候補とする。時刻や乱数など非決定的な処理、読み取り専用として解析できないSQL、上限で切れた結果は事前規則で除外する。実行失敗、列・結果の不一致、正規化後に同じSQLになった候補は、それぞれ件数と理由を残す。成功したケースだけを分母にして除外数を隠さない。

SQLごとの上限は5秒、結果は10,000行までとし、ローカルCPUで実行する。主要指標は、結果一致を確認した候補の誤拒否率。変換別の適用数、除外数、実行失敗数、空結果数、問題コードの内訳を併記する。元データと個々の結果値はGitやNotionへ保存しない。

## 注釈の値が残る誤りで検査を比較する

診断ログの再集計後に追加した次の検討案であり、まだ実施していない。SQLの完全一致と注釈の照合を片方ずつ外しても同じ拒否件数になるため、その違いが現れる候補が必要である。

患者IDや検査項目の文字列を残したまま、比較演算子や条件の結び方を変える候補を、同じ公開データから作る。単に値や文字列の存在を調べる検査と、条件の構造を調べる検査を区別する狙いがある。候補を作った操作だけで臨床的な誤りと断定せず、対象とする変換、妥当性の判断方法、結果が変わらない場合の扱い、除外基準を実行前に固定する。この実験でも、現実の生成エラーの頻度は推定しない。

## この追加評価でも分からないこと

既存ログの再構成は、実際に生成されたエラーの分布を示さない。結果を保つSQL変換も、現実の生成モデルが作る別解の分布を示すものではない。医療者への効果、臨床シナリオの妥当性、未知の誤りの自動修復は、この二つの評価では解消しない。

現状の採否判断を見直す材料として、まず検査の役割と妥当な別解への制約を明らかにする。追加評価で数値が増えたことだけを、CHIへの新規性や採択見込みの根拠にはしない。
