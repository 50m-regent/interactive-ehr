\title{Evaluating Cross-Layer Integrity in Updates to Generated Clinical Interfaces}
\author{Anonymous Author(s)}

\begin{document}

\begin{abstract}
Data-backed interfaces can remain executable while an update breaks correspondence between a request, query, result, and presentation. We study this problem through reference-based regression testing for generated clinical interfaces. Using EHRSQL-2024 and MIMIC-IV Demo, we construct 763 update pairs spanning eight injected fault types and compare four validation conditions in 6,104 validations. Candidates are selected to pass local checks; their 100\% leakage is therefore a construction property. Artifact-level contracts accept 48.10\% of inconsistent candidates. Two cross-layer implementations reject all injected inconsistencies and accept all reference-valid candidates, but share expected values and checking functions. We document which checks expose each fault and distinguish fault-type reporting from restoration using a saved valid artifact. The results characterize coverage of a predefined fault model with trusted reference information. They do not establish robustness to natural generation errors, independent benefits of graph storage, or improvements in clinicians' work.
\end{abstract}

\section{Introduction}

Clinical records may contain more information than a person can review for a particular task. Selecting and arranging that information introduces choices about patient, item, period, source, and presentation. An interface can reduce what is shown while also hiding a mismatch between what was requested and what was retrieved. We investigate a technical way to expose such mismatches during updates. This paper does not measure a person's information-processing capacity or demonstrate a reduction in review burden.

For illustration, a preoperative assessment might summarize recent findings, whereas a follow-up view might combine selected trends and current values. These are motivating design examples, not validated clinical requirements or evaluation tasks. They motivate a data-backed interface whose information changes with a request, and the need to check the correspondence from request to presentation.

Existing technical checks leave a gap relative to that goal. SQL syntax, query execution, result schemas, interface code, and rendering can each be validated independently. Yet every artifact may pass while a query selects another patient, omits a time filter, leaves a result from the previous update, or connects a widget to the wrong data. Better text-to-SQL accuracy does not ensure that the same information need survives subsequent execution, connection, and presentation. A system can therefore work mechanically while returning information that does not answer the user's request.

We call a broken semantic correspondence between a scenario-grounded information need and the displayed information a \term{cross-layer inconsistency}. We evaluate a generated clinical interface as a process spanning an information need, SQL, an execution result, and a presentation, rather than as a collection of independently valid artifacts. Correctness here does not mean that the complete clinical judgment is correct. It means that the patient, item, time, aggregation, source, presentation, connection, and version specified for an update remain consistent across layers.

Research on generative and malleable interfaces connects requests to interfaces through intermediate representations. Jelly maintains an evolving task-driven data model~\cite{cao2025jelly}; Bridging Gulfs exposes semantic design intent~\cite{park2026bridging}; SimStep supports inspection and correction across task-level abstractions and evaluates fidelity across transformations~\cite{kaputa2026simstep}. Our comparison focuses on eight injected faults in request-to-data correspondence, applying four specified checking conditions to the same candidates.

We built a reference-based regression-testing framework for cross-layer inconsistencies in updates to clinical data-backed interfaces. EHRSQL-2024 supplies annotated questions and reference SQL~\cite{lee2024ehrsql}; MIMIC-IV Clinical Database Demo v2.2 supplies execution data~\cite{johnson2023mimic}. The framework constructs minimal data and presentation artifacts and injects eight predefined fault types. It does not run a UI-generating model or test rendered screens. A separately implemented oracle checks candidates against a contract: selected fields and expected values derived from the known target case. Both full validation conditions also receive that contract. Thus, the evaluation examines whether predefined checks cover injected faults when trusted reference information is available.

We ask:

\begin{description}
  \item[RQ1] Which of the eight fault types can be constructed while preserving the local checks?
  \item[RQ2] How do local validation, artifact-level contracts, and cross-layer contracts differ in inconsistency leakage, valid-update acceptance, and fault-type coverage?
  \item[RQ3] For which rejected injections does a reported fault type enable one restoration from a saved valid artifact?
\end{description}

After freezing the evaluation method, we ran the test split once. We formed 763 update pairs from 134 question templates and performed 6,104 validations. Local validation accepted all inconsistent candidates because passing that condition is required for inclusion. Artifact-level contracts accepted 367; both full conditions rejected all inconsistent candidates and accepted all reference-valid candidates. The full conditions share core checking functions as well as expected values. Their agreement is an implementation consistency check, not independent evidence that storage representation has no effect.

The paper contributes a bounded evaluation artifact:

\begin{itemize}
  \item A fault model for request, query, result, and presentation correspondence, with eight deterministic injection rules and explicit construction gates.
  \item A reproducible protocol that pairs reference-valid and inconsistent candidates, applies four specified checking conditions, and records detection, type reporting, and reference-assisted restoration.
  \item An analysis connecting implemented checks to detected and missed fault types, with explicit reference assumptions.
\end{itemize}

This is a technical evaluation. It does not evaluate the clinical validity of the scenario models, clinical safety, diagnostic accuracy, usability, cognitive load, clinical outcomes, or deployment. We treat technical correspondence and user benefit as separate evaluation targets.

\section{Related Work}

\subsection{Generative and Malleable User Interfaces}

Generative-interface research has moved from producing screens from natural language or examples toward helping users understand, edit, and reuse generated artifacts. DirectGPT supports iterative work with large language models by combining conversation with direct manipulation and reference resolution on generated objects~\cite{masson2024directgpt}. DynaVis combines conversational generation and editing of visualizations with direct interaction on the generated interface~\cite{vaithilingam2024dynavis}. Both treat generated artifacts as objects that continue to change, rather than as one-shot outputs.

Intermediate representations provide structure for such updates. Jelly places a task-driven data model behind a generated interface and propagates task changes into data and views~\cite{cao2025jelly}. Bridging Gulfs uses semantic representations to narrow gaps among user intent, model interpretation, and interface output~\cite{park2026bridging}. SimStep separates graphs for concepts, scenarios, learning objectives, and interfaces so that assumptions can be inspected and repaired across stages~\cite{kaputa2026simstep}. Across these systems, intermediate representations become points of contact for inspection and repair.

We study a narrower question: which specified checks cover faults injected into an update with known reference information? We do not compare initial generation quality or editing experience. The graph and tabular conditions provide two access paths to shared checking logic; they do not isolate the effect of storage architecture.

\subsection{Inspection and Repair in Human-AI Collaboration}

People do not simply accept or reject generated suggestions. Ignore, Trust, or Negotiate documents how clinicians ignore, trust, and negotiate AI suggestions, and argues for interactions that expose uncertainty and supporting information~\cite{sivaraman2023ignore}. For generated interfaces, an undifferentiated error message may be less actionable than a diagnosis that identifies the broken relationship and the scope affected by a repair.

A rejection and an actionable diagnosis need not coincide. We record whether a validator rejects a fault, whether it reports the injected type, and whether a routine using that type and a saved valid artifact restores the candidate. The latter two measurements are coupled by the restoration procedure. Neither measures whether a person can locate or correct an error from the diagnosis.

\subsection{From Natural-Language Questions to Data and Presentation}

Text-to-SQL research evaluates whether a system can generate executable SQL that answers a natural-language question. EHRSQL-2024 provides a shared task for electronic health records that includes both answerable and unanswerable questions~\cite{lee2024ehrsql}. Its central challenges include generating SQL for answerable questions and abstaining when a question cannot be answered.

We do not compare SQL-generation performance. We use reference SQL as a starting point and examine inconsistencies that arise during subsequent updates. Even when a correct query was previously available, a question, query, result, or presentation can advance to a different version during an update. An executable query can also refer to a patient or time range that differs from the request. Validation must therefore cover not only question-to-SQL correspondence, but also SQL-to-result versioning, result-to-presentation compatibility, data-presentation connections, and update versions.

\subsection{Model Transformation and Consistency}

Bidirectional-transformation research has formalized how updates to structured sources and views should correspond. Lenses define laws for transformations between a source and its view~\cite{foster2007lenses}. Metamorphic testing has also been proposed for model transformations where enumerating every correct output is difficult, using invariant relations instead of complete expected outputs~\cite{he2018metamorphic}.

The oracle problem concerns how a test distinguishes expected behavior from a fault; prior work includes specification-based, derived, and partial oracles~\cite{barr2015oracle}. Our implementation uses a restricted reference oracle: it requires equality of selected query, result, and binding fields from a known target. It does not implement lens laws or establish general semantic equivalence. The connection to consistency testing is methodological; the proposed artifact specializes fault injection and reference checking to boundaries in data-backed interface updates.

\section{Clinical Problem and Evaluation Scope}

\subsection{Scenario-Specific Information Needs}

Our design process organized two clinical scenarios that motivated this work: a preoperative anesthesia clinic and follow-up after thyroid surgery. In the preoperative scenario, the surgery date anchors a one-time assessment that brings together patient demographics, the planned procedure, lifestyle and allergy information, medical and treatment histories, recent examinations, and prior anesthesia records. The clinician ultimately compiles a list of anesthesia risks. This scenario emphasizes a broad view of the patient's latest state.

In post-thyroidectomy follow-up, the visit date anchors the review. The clinician examines thyroid function, ultrasound findings, and levothyroxine replacement dose. In this design example, thyroid function and dose use a twelve-month trend, while other tasks use the latest values. Appropriate views therefore combine longitudinal trends with current summaries.

Figure~\ref{fig:scenario-to-value} illustrates these differences and the scope of this paper. The scenarios are design examples, not clinically validated ground truth for our benchmark. Their task models have not completed expert validation. We use them to explain why the information and presentation retrieved from the same electronic health record must depend on a clinical scenario.

\subsection{From Technical Correspondence to User Value}

At least three conditions separate a generated clinical interface from value to a clinician. First, domain experts must define questions, required information, and completion criteria for a clinical scenario. Second, the system must translate the resulting information need into appropriate retrieval and presentation. Third, a clinician must use the presentation to review necessary information and perform the clinical task. This paper tests selected reference checks related to the second condition, using a known target; it does not evaluate that condition as a whole.

Our results cannot show that cross-layer integrity reduces verification effort or missed information. We examine selected technical checks separately from user experience. In a later user study, information correctness should be assessed alongside completion time and preference, so that a fast but incorrect response is not counted as a successful clinical task.

\subsection{Defining an Information Error}

Information can be wrong at several stages. This study does not determine whether source records are factually correct, whether a scenario's task model is clinically appropriate, or whether a clinician makes the correct judgment after viewing the interface. We define an \term{information error} within our scope as a state in which information delivered to the screen does not match a specified information need in at least one of eight dimensions: patient, item, time, aggregation, source, presentation, connection, or version. A cross-layer inconsistency localizes such an error to a relationship between artifacts.

This definition distinguishes an ill-formed query from a well-formed query that retrieves different information. The local validator checks permitted SQL form and artifact compatibility. Detecting a mismatch with a request additionally requires a trusted expectation; the full conditions in this experiment receive that expectation from the target case.

\section{Defining Cross-Layer Integrity}

\subsection{Information Flow and Detection Mechanism}

We model four layers: information need, SQL, execution result, and presentation component. An information need includes the target patient, clinical item, time, aggregation, source, and expected presentation. SQL translates that need into a database operation. An execution result has a version corresponding to the SQL, input, and time of execution. A presentation component refers to a result and displays it using a form compatible with its shape.

Figure~\ref{fig:detection-mechanism} illustrates a single patient mismatch. The implementation derives expected values from annotated target cases and reference SQL, rather than extracting a validated clinical intent from arbitrary prose. It compares selected query, result, reference, and presentation fields and returns issue codes and type labels. The figure depicts the conceptual flow; exact checks and the privileged information used by the oracle and restoration routine are specified below.

For conceptual organization of the fault model, we express the required correspondences of an update candidate $c$ as a conjunction. The implemented checks use selected reference fields; the equation is not a general semantic-equivalence test:

\begin{equation}
I(c)=P(c)\land D(c)\land T(c)\land A(c)\land S(c)\land V(c)\land L(c)\land R(c)
\end{equation}

$P$ denotes patient, $D$ clinical item, $T$ time, $A$ aggregation, $S$ source, $V$ presentation form, $L$ the data-presentation link, and $R$ the correspondence between SQL and result versions. These symbols organize the fault model rather than specify the exact implementation of the oracle. Each inconsistent candidate receives one injection rule; that mutation may trigger several failed checks. Passing the selected reference checks is narrower than satisfying general semantic equivalence.

\subsection{Eight Inconsistency Types}

Table~\ref{tab:mutations} defines the eight inconsistencies. A patient inconsistency preserves the patient in the information need while changing the patient condition in SQL to another valid candidate. An item inconsistency changes the selected column or aggregation target. A time inconsistency changes a condition associated with a time point or interval. An aggregation inconsistency replaces a count, maximum, minimum, average, or related operation with another valid operation.

A source inconsistency changes the recorded provenance-table metadata while leaving SQL and its result fixed. It does not execute a query against an alternative table. A presentation inconsistency changes the baseline component type while preserving SQL and data: a metric becomes a dataframe, or a dataframe becomes another table component. The label denotes violation of a predetermined presentation rule; it does not establish that the alternative is misleading or clinically inappropriate. A connection inconsistency redirects the widget to the source data node with compatible columns and mapping. A stale-result inconsistency attaches the source result to the target query when the two result digests differ.

These categories are not an empirical distribution of errors observed in clinical practice. They form a fault model that makes specific relationships testable. Because we inject one inconsistency into each candidate, the results do not characterize performance on compound failures.

\section{Evaluation Framework}

\subsection{Constructing Baseline Cases}

The inputs are answerable questions and reference SQL from EHRSQL-2024. Unanswerable cases lack reference SQL from which to construct a baseline interface, so we exclude them from the primary evaluation while recording their count. Reference queries are executed read-only against the SQLite version of MIMIC-IV Demo v2.2. We reject statements that write data, contain multiple statements, or use disallowed syntax before execution, and impose a five-second limit on each query.

We use a metric component when an execution result is a single value and a dataframe when it contains multiple rows or columns. Empty results are retained as results with a defined column structure. Each baseline case stores annotated patient, item, time, and aggregation fields associated with the question template, parsed SQL, result shape, data node, presentation component, and version identifiers for these artifacts.

We group cases by question-template string and consider ordered source-target pairs within each group. For each template and fault type, a seeded hash orders eligible descriptors; we retain the first pair that passes construction checks. Thus, there is at most one pair per template and type. A template can contribute to several types, and the same underlying source or target case can recur. These are constructed transitions, not observed sequences of user edits.

For inclusion, a valid candidate must pass the reference oracle, its injected counterpart must fail that oracle, and the inconsistent candidate must pass local validation. This last gate intentionally concentrates the benchmark on locally admissible faults and makes 100\% local leakage true by construction. It is not an estimate of failure prevalence or of local-check accuracy on naturally generated candidates.

\subsection{Reference Oracle and Its Dependence on the Contract}

The oracle is implemented separately from mutation generation and validator dispatch, but it uses the same target-case contract. It checks the question checksum, normalized reference-SQL checksum, provenance-table list, result-query checksum, result digest, column checksums, widget identifier, data-node binding, fields, and component type. This is equality of selected reference fields, not an independent judgment of clinical intent or SQL semantic equivalence.

The oracle does not compare the complete JSON document. It nevertheless requires the selected identifiers, column order, SQL checksum, and other contract fields to match. A semantically equivalent alternative query or presentation may fail these reference checks. Valid candidates in this experiment are constructed from the reference itself; their acceptance cannot estimate acceptance of diverse valid solutions. Separate code paths reduce some implementation coupling, but common reference errors can affect generation, the oracle, and full validation together.

\subsection{Four Validation Conditions}

We apply the same candidate to the four conditions in Table~\ref{tab:conditions}. \condition{Local validation} checks SQL syntax and permitted read-only form, node-reference existence, a nonempty column schema, widget-field membership, and metric-shape compatibility. Query execution occurs during candidate construction, not during the timed validator call. No browser rendering is checked. \condition{Artifact-level contracts} additionally compare recorded provenance with tables parsed from SQL, the result's query checksum with current SQL, and the widget type with the type assigned from result shape. Despite its short name, this condition includes these adjacent-artifact checks. It does not compare the target request annotations or target binding against the full reference contract.

The \condition{graph-based cross-layer contract} follows the question, target data artifact, and widget references and compares them with the target contract. The \condition{tabular cross-layer contract} first compares flat fields against the same expected values. Both then call the same semantic-query, target-data, and target-widget checking functions. The semantic-query function checks annotated literals or normalized fragments and also requires equality with the normalized reference-SQL checksum. Neither implementation infers correctness from unrestricted natural language. These are two access paths over shared checking logic, not independently implemented storage architectures. Their agreement cannot establish a causal effect of storage form.

\subsection{Fault-Type Reporting and Reference-Assisted Restoration}

A diagnosis contains an issue code, a layer label, and sometimes a fault-type label. We score fault-type coverage when the injected type is present in the set of reported type labels. We do not require a unique diagnosis, penalize extra type labels in this score, or verify an exact node or edge location. We therefore interpret this metric as fault-type coverage.

The restoration routine receives the injection type and the saved valid candidate. If the reported labels include the injected type, it copies the complete target data artifact for SQL, provenance, or stale-result faults, or the complete valid widget for presentation and connection faults. Otherwise it returns the candidate unchanged. The restored candidate must pass both the same validator and the reference oracle.

This procedure tests recovery with privileged reference information. It does not infer the injected type solely from the diagnosis, synthesize a minimal patch, or discover a correct state from an unknown error. Restoration attempts are gated by the known invalid label and validator rejection. Consequently, this protocol does not measure the risk of modifying an incorrectly rejected valid update.

\subsection{Evaluation Protocol}

Figure~\ref{fig:protocol} summarizes the protocol. On development data, we prioritized 50 cases with distinct question templates to verify SQL execution and baseline conversion. On validation data, we checked candidate counts per inconsistency type, the number of represented templates, label agreement, and the requirement that saved outputs contain no sensitive data. A planned column-order mutation could not be generated, so before inspecting the test split we replaced it with the presentation mutation. We left all other mutations, metrics, analyses, and stopping rules unchanged.

After the validation-data criteria were met, we froze the evaluation code, configuration, and analysis in a versioned execution manifest. We then ran the test split once. No generative or external model was called during evaluation.

\subsection{Metrics and Statistical Analysis}

The primary metrics are \term{inconsistency leakage rate} and \term{valid-update acceptance rate}. Leakage is the fraction of injected inconsistent candidates accepted; valid acceptance is the fraction of reference-valid candidates accepted. Secondary metrics are fault-type coverage, reference-assisted restoration success, and mean validation time per candidate. Type coverage divides correctly reported injections by all 763 injections. Restoration is reported both per attempted restoration and per injected fault.

We calculate paired condition differences and use 10,000 question-template cluster bootstrap resamples for 95\% intervals. This retains dependence among candidates from one template. It does not address shared patients, overlapping cases, or common injection rules across templates. The intervals describe variation in the retained template sample under the fixed fault model, not uncertainty about natural error rates or new hospitals. Degenerate intervals arise when all resampled clusters have the same contrast; they are not proof of universal performance.

\subsection{Data Management and Reproducibility}

Released artifacts do not contain raw data, question text, reference SQL, patient identifiers, or patient-level result values. They contain hashed case identifiers, input and candidate checksums, inconsistency type, decision, diagnosis, restoration outcome, aggregates, and execution environment. We froze formal results as JSON and JSON Lines, then converted them to TSV in an independent procedure that recomputed counts, primary metrics, and confidence intervals. The recomputed values matched the original summary.

\section{Results}

\subsection{Baseline Cases and Candidates}

The test split contained 1,167 cases. We evaluated the 934 answerable cases with reference SQL and excluded 233 unanswerable cases from the primary evaluation. Reference SQL executed and baseline artifacts were constructed successfully for all 934 cases; 82 yielded empty results with defined column structures. We formed 763 before-and-after update pairs from 134 question templates. For each pair, we created one valid and one inconsistent candidate and applied four conditions, yielding $763\times2\times4=6{,}104$ validations. Candidate labels disagreed with the reference oracle in zero cases.

We generated 52 patient, 55 item, 106 time, 34 aggregation, 134 source, 134 presentation, 129 connection, and 119 stale-result inconsistencies, totaling 763. For patient, item, time, and aggregation mutations, we skipped cases where no alternative SQL could change exactly one semantic dimension. Candidate counts therefore differ across types and depend on the data and question forms.

Construction recorded 3,420 failed pair-building attempts: 1,140 for patient, 1,383 for item, 576 for time, and 321 for aggregation; none were recorded for the other types. These count attempted constructions, not distinct excluded questions or patients. Retaining only the first successful pair per template and type selects faults that this data and construction procedure can express.

\subsection{RQ1: Inconsistencies That Pass Local Validation}

Local validation accepted all included inconsistent candidates, as required by the construction gate. This confirms that the gate operated as specified; it is not an empirical discovery that local validation misses all real errors. The comparison asks which additional checks detect these deliberately selected faults.

Leakage under artifact-level contracts varied by inconsistency type (Table~\ref{tab:mutation-results}). Its three additional checks rejected every provenance-metadata, presentation-rule, and stale-result fault. In contrast, 92.73\% to 98.08\% of patient, item, time, and aggregation faults leaked, as did every connection fault. These checks omit target-request and target-binding comparisons; some semantic injections were nevertheless rejected because the resulting artifact also violated a checked shape or mapping rule.

Artifact-level contracts rejected 396 inconsistent candidates and reported the injected type in 387, giving 50.72\% coverage over all 763 injections. \subsection{RQ3: One-Step Reference-Assisted Restoration}

Local validation rejected no inconsistent candidate and attempted no restoration. Artifact-level contracts triggered 396 attempts; 387 passed both the validator and reference oracle, or 97.73\% of attempts and 50.72\% of all injections. In the other nine cases, the reported types did not include the injected type, so the restoration routine returned the unchanged candidate.

Both full conditions enabled restoration of all 763 injections using the saved valid data artifact or widget. Because restoration is gated by correct type reporting and copies a known valid component, these successes are coupled to the type-coverage result. They do not constitute an independent demonstration of automatic repair capability. No valid candidate was rejected, and the protocol would not attempt restoration of a candidate labeled valid even if it were rejected.

\section{Discussion}

\subsection{What the Controlled Comparison Establishes}

The benchmark identifies gaps between the specified checks under a known-target assumption. Artifact-level checks detect provenance metadata, baseline presentation mapping, and query-result version mismatches. They can also reject a semantic-query mutation when it changes result shape, without reporting the injected semantic type. The full conditions add target-query and binding checks and reject all retained injections.

This is evidence about coverage of the implemented fault model. Both the fault generator and the check designer know the relationships to change or preserve. In particular, comparing normalized query checksums makes rejection of a changed reference query unsurprising. A useful next comparison would separate annotated-slot checks, reference-checksum checks, result checks, and binding checks, and include semantically equivalent valid alternatives. Such a comparison would identify the contribution of each check beyond exact reference matching.

\subsection{Implications for Data-Backed Interface Updates}

The practical design question is where a system obtains trustworthy expectations. A stored binding or query-result version may be available after an update, while the correct SQL for a new natural-language request may not be. Our full validators receive both. A system that generates expectations with the same model that generates its output can produce mutually consistent but jointly wrong artifacts. The present evaluation does not resolve that problem.

For developers, the fault model provides a way to specify which reference fields a check needs and which change it can detect. It also makes a distinction visible: provenance metadata disagreeing with SQL is different from SQL querying an inappropriate source, and violating a baseline widget rule is different from misleading a user. Evaluations should name those distinctions rather than combine all rejections as evidence of clinical correctness.

\subsection{What the Graph and Tabular Agreement Means}

Both full conditions access the same target contract and call shared query, data, and widget checks. Their identical results show that the two tested access paths give consistent outcomes on this suite. They do not establish storage-independent performance, scalable graph propagation, or an advantage for either representation. Those questions require independent implementations and measurements of their intended tasks.

Prior generative-interface work uses intermediate representations to support inspection and editing~\cite{cao2025jelly,park2026bridging,kaputa2026simstep}. Our benchmark focuses on a narrower developer-facing problem: checking data correspondence against a reference. Whether those checks improve how people inspect and edit generated interfaces remains open.

\subsection{Evaluating Use in Generated Interfaces}

The present artifact is designed for developer regression checks. Extending it to generation-time validation requires testing naturally generated failures and the availability of trusted expectations. The illustrative clinical scenarios do not establish how often the eight faults occur or how consequential they are in practice.

A subsequent technical study should freeze validators before collecting naturally generated updates, include valid alternatives, obtain reference judgments independent of validator design, and compare against established checking methods. If the contribution concerns clinician verification, an additional study should compare the same interface with and without diagnoses, using expert-reviewed scenarios and reporting faulty-update acceptance, valid-update acceptance, review time, and repair quality separately. Such studies may show a benefit, a cost, or no effect.

\subsection{Restoration Is a Different Capability from Repair}

Copying a saved valid artifact is useful when a trusted target state exists, but it does not solve correction of an unknown generated state. Our routine also receives the injected type, and replaces a whole data artifact or widget rather than computing a minimal patch. A practical repair evaluation must hide injection metadata, withhold the complete valid target, test collateral changes, and judge correctness independently. The current 100\% restoration result should not be used as a claim that a diagnosis alone supports reliable automatic repair.

\section{Limitations and Ethics}

First, we inject one inconsistency at a time using deterministic rules. The generated candidates do not represent the distribution of errors that a generative model produces naturally. A condition that achieved 100\% on single faults may not perform similarly on compound failures, ambiguous requests, or unknown presentation components. Future work should apply the frozen validators to naturally occurring candidates and qualitatively analyze failures outside the taxonomy.

Second, the benchmark uses the known target query and its executed result, not merely a previously valid query. It therefore assumes that a trusted state is available for the requested update. This assumption is restrictive for generative interfaces. Question interpretation, initial generation, abstention, and alternative valid realizations require separate evaluation.

Third, we use only MIMIC-IV Demo v2.2 and EHRSQL-2024 question templates. The preoperative anesthesia and post-thyroidectomy scenarios illustrate the problem but are not formal evaluation cases. Candidate counts differ across inconsistency types because result shapes and valid alternatives differ. We cannot generalize the findings to other clinical scenarios, data models, institutions, complex visualizations, or updates spanning multiple sources. Applicability to non-healthcare data and workflows is also untested.

Fourth, full validation and the oracle share the target reference; graph and tabular implementations additionally share core checking functions. This common dependency limits evidence from agreement. No ablation separates reference-SQL equality from annotated-slot or relationship checks. Valid candidates cover the chosen reference encoding, not the space of semantically equivalent queries and displays. The evaluation cannot establish false-rejection rates for such alternatives.

Fifth, this is a technical evaluation on publicly available deidentified demo data. Reference SQL is a technical baseline, not a clinically validated definition of appropriate presentation. We did not measure effects on verification burden, acceptance of faulty updates, or clinical judgment. We make no claims about clinical safety, diagnostic accuracy, usability, cognitive load, clinical outcomes, deployment, or generalization across institutions. Any human-participant study will be separate work conducted only after applicable ethics review, permission, recruitment, consent, withdrawal, and data-management procedures are established.

Released artifacts contain no question text, reference SQL, patient identifiers, or patient-level result values. We state the conditions of use and provenance for MIMIC-IV Demo and EHRSQL-2024 and include only releaseable checksums, categories, decisions, and aggregate statistics in reproducibility materials.

\section{Conclusion}

We present a reference-based regression-testing artifact for request, query, result, and presentation correspondence in clinical interface updates. Eight deterministic injection rules yielded 763 paired updates and 6,104 validations on EHRSQL-2024 and MIMIC-IV Demo. The artifact makes construction gates, expected fields, diagnostic scoring, and restoration inputs explicit.

All injected candidates passed local checks by construction. Artifact-level contracts accepted 48.10\% of them. The two full conditions rejected every injected inconsistency and accepted every reference-valid candidate while sharing target information and checking functions. These results describe coverage of this predefined fault model. Type reporting and copying saved valid components do not establish fault localization or repair of unknown generated states.

The practical question is which trusted expectations an interface developer can obtain and check during an update. The next evaluation should apply frozen checks to naturally generated updates and valid alternatives, then compare their decisions with independently assessed outcomes. Whether these checks help people inspect and correct an interface remains open.
